# Message T3 Code agents from Ember

Run the standalone Node bridge on a host that can reach your Ember deployment and the T3 environment's MCP endpoint. The existing Ember Worker and web app need no changes. Each top-level message mentioning the bot creates a dedicated T3 thread and worktree. Mention the bot in replies to that Ember message to continue the same T3 conversation. The bridge posts results into the original Ember thread.

## Set up

1. Install Node 24.22 or newer and pnpm 10.18.3. From the repository root, run `pnpm install --frozen-lockfile`.
2. In Ember's administration, create a dedicated bot. Copy its full API key. Identify the exact Ember user and room IDs to permit. Names are not IDs. Bot DMs also need their room ID allowed.
3. In T3 Code, copy the MCP endpoint from **Settings > Environments**. Identify the environment and project IDs using T3's environment/project tools or your existing authorized MCP client. Use a disposable project for the first check.
4. Copy `packages/t3-bridge/config.example.json` outside the checkout to `/absolute/private/config.json`. Replace every `REPLACE` value. Set `t3Origin` to the origin permitted for links returned by T3. Set `dataDir` to a new private directory on persistent local storage. Generate `webhookSecret` with `node -e 'console.log(require("node:crypto").randomBytes(32).toString("base64url"))'`. Restrict the config to mode 0600. Keep both files and the data directory out of source control and shared backups.
5. Run `pnpm --filter @ember/t3-bridge start oauth /absolute/private/config.json`. Open the printed authorization URL and authorize the intended T3 identity. The CLI handles MCP OAuth discovery, dynamic client registration, PKCE and state verification. The callback binds only to `127.0.0.1:8791`. If the bridge host is remote, forward that port to your browser machine first, for example `ssh -L 8791:127.0.0.1:8791 bridge-host`. OAuth setup times out after ten minutes.
6. Run `pnpm --filter @ember/t3-bridge start check /absolute/private/config.json`. Expect `T3 capabilities, environment and project verified.` A failure does not launch an agent.
7. Run `pnpm --filter @ember/t3-bridge start serve /absolute/private/config.json`. Expect `Ember T3 bridge listening.` Run it under your service manager with an absolute working directory, a dedicated OS account, persistent storage and restart on failure.
8. Expose port 8790 through your HTTPS reverse proxy. Disable request-path logging for this route. Set the Ember bot's webhook URL to `https://bridge.example.com/webhook/<webhookSecret>`. Ember sends no configurable authentication header, so the random URL path is the incoming bearer credential. The bridge additionally verifies the configured bot key in the payload. Anyone holding these credentials can impersonate allowed users. Protect the URL as a secret. Loopback HTTP is supported for local development.
9. In the allowed Ember room, mention the bot with a small authorized task. Expect a quick webhook acknowledgment and a reply in that message's thread after the T3 run and its delegated work finish. Reply in that thread and mention the bot again to continue. Open T3 for approvals, questions, steering, cancellation and full output.

`runtimeMode` defaults to `approval-required`. Any broader mode must be explicitly set by the operator and permitted by the OAuth identity. The bridge never handles approval requests or bypasses approval. It does not reuse or steer the orchestrator thread. Each conversation requests a new worktree; the configured project must support worktrees. Provider and model selection use T3's defaults for the authorized identity.

## Inspect and recover

Run `pnpm --filter @ember/t3-bridge start status /absolute/private/config.json`. While the service runs, the command queries its authenticated status route on loopback. When stopped, it reads the SQLite store. Status includes job IDs, conversation IDs, state, known T3 links and observation errors. It excludes bot credentials and prompts. `/health` only reports process readiness. It does not verify ongoing T3 connectivity.

The service polls every five seconds. It advances one state per conversation per poll, and processes conversations sequentially. A slow MCP endpoint can delay other conversations. Run observation retries on subsequent polls. A run waiting for input or approval remains active until handled in T3. Lost history, authorization expiry and invalid protocol responses remain visible in status. The bridge uses `t3_thread_wait` with `untilDelegatedWorkSettled` to observe execution completion independently of sidebar settlement. Replies contain only local assistant messages from its reported result run, including a continuation after delegated work, never inherited or child transcripts. Native T3 links are validated against the configured environment and accepted thread; hosted links must match the configured origin. The complete reply fits Ember's 10,000-character limit, preserves a truncation notice and link, and is escaped as text; use the T3 link for the full result.

A `submitting` or `delivering` checkpoint after a crash becomes `unknown`. Network failures and unverified acknowledgments also become `unknown`. Later messages in that conversation stay queued. The bridge does not retry uncertain execution or callback POSTs, because that could duplicate coding work or Ember replies. Stable request IDs are supplied, but T3 retry retention has not been verified. An Ember reply contains an `Ember delivery <room>:<message>` marker for manual reconciliation.

Stop the service before either recovery command. Inspect T3 and Ember first.

- To resume observation of a verified accepted run, run `pnpm --filter @ember/t3-bridge start resolve /absolute/private/config.json '<room>:<message>' '<threadId>' '<runId>'`. This validates the exact run, project, environment, top-level thread and permission mode before binding it. It does not submit a new task. Restart `serve` to observe and post its result. Use this only when its result has not already been posted to Ember. This command does not recover the original T3 link; subsequent output says the link is unavailable.
- If an uncertain reply already arrived, or you deliberately abandon an uncertain job after inspection, run `pnpm --filter @ember/t3-bridge start dismiss /absolute/private/config.json '<room>:<message>'`. This releases the queue without submitting or posting anything. It does not cancel T3 work. Dismissing an unknown root launch leaves no binding, so its followups cannot proceed. Use `resolve` for an accepted root run or start a fresh top-level Ember message.

The SQLite database holds accepted messages, run state, conversation bindings and pending reply text. Keep it on local disk with normal SQLite locking. One service process owns each data directory, enforced by SQLite exclusive locking. Do not run it on network storage or share it across replicas. Back up the entire private directory only while the service is stopped. Dedupe records are retained indefinitely. There is no automatic compaction or worktree cleanup in this initial integration.

The data directory binds to the Ember origin, bot key, T3 endpoint, project, environment, link origin and runtime mode. Changing one requires a fresh data directory or a separately reviewed migration. This prevents accidental replay into another project. Drain and stop the service before rotating the bot key or changing those settings. User and room allowlists apply at admission; removing an ID does not cancel previously accepted work.

OAuth credentials are endpoint-bound and stored atomically in `oauth.json` with mode 0600 and service-account ownership. They are plaintext bearer credentials protected by filesystem permissions, not encryption at rest. Protect the host, disk and backups accordingly. Refresh tokens are handled by the MCP SDK. Stop the service and repeat `oauth` when authorization is revoked or cannot refresh. Never paste tokens into chat or webhook configuration. HTTPS is required except exact loopback hosts; redirects are rejected. Ember callbacks are constructed from the configured origin and key, never fetched from an arbitrary payload URL.

## Validation boundary

`pnpm --filter @ember/t3-bridge test` runs real local HTTP MCP and OAuth protocol fixtures, bridge ingress, callback delivery, restart, dedupe, escaping, unknown-state and executable checks. These fixtures do not prove a live T3 provider or deployed Cloudflare integration. Protocol grounding uses the existing D3 adapter's T3 source reference `0c832589a0369bd7d4ac9b074c0ea6ce93d7f4a5` and the installed T3 tool contracts. Startup checks capabilities and environment identity instead of trusting that revision.

Before using a production project, coordinate a disposable live pilot. Verify OAuth, a new conversation, a queued reply, approval in T3, a long run, restart while observing, Ember reply delivery and token revocation. Record the actual T3 revision and provider outcomes. No live coding task or Ember message was sent during implementation tests.
